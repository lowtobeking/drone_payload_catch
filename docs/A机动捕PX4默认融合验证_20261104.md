## 复验经过与排错结论

1. 初始完整参数快照显示 A 的 PX4 仍为 `GPS_CTRL=7、EV_CTRL=0、BARO_CTRL=1、HGT_REF=1、MAG_TYPE=0、SYNCT=1`，所以此前地面验收成功不等于本次开机后正在融合。原始 1127 项快照保存在 `report/a_deployment_20261104_height30/px4_parameters_before_fusion.json`。
2. 首次切到动捕参数时额外把 `EKF2_BARO_CTRL` 设为 0。桥接虽持续转发，PX4 的 EV 三项融合标志仍为 `false`。随后只恢复 `BARO_CTRL=1` 并经飞控重启读回；这个设置与以前成功的地面 XYZ/航向融合更一致。恢复气压计后，`z_valid` 先恢复；最终同一窗口复验才观察到 EV 三项全部有效。**不能把 BARO 改动单独认定为唯一根因**，此前短窗口与观察时序也影响了判断。
3. `run_a_solo_mocap.sh` 原先在 ROS `setup.bash` 前使用 `set -u`，又覆盖 `PYTHONPATH`，导致启动或预检找不到 ROS Python 模块。现已修正，发布为版本化 A 机当前程序。单机 `execute` 入口要求从动捕组合入口调用；`check` 模式仍可只读使用。
4. 预检原示例 UDP MAVLink 端点收不到 A 的心跳。项目当前组合入口使用 `passive:eno1` 读取真实飞控完整参数；该方式已在本次地面预检中读到所有参数。不要拿无法连通的 `udpout:127.0.0.1:18570` 示例地址当成现场端点。
5. A 的 Wi-Fi 地址 `192.168.1.5` 一度无法 SSH；`nvidia-desktop.local` 解析出 Mesh 地址 `192.168.1.101`，从电脑有线地址 `192.168.1.123` 连接成功，严格核对原 SSH 主机密钥及板卡序列号 `1612425621719`。这是本次诊断连接路径，不代表 Wi-Fi 故障已修复。

## 后续运行注意事项

- **不要关闭 `UXRCE_DDS_SYNCT`。** 动捕服务器时间与 Jetson 不一致已由接收时间模式隔离；DDS 同步处理的是 Jetson 与 PX4 两套时钟。本次同步状态新鲜，且最终 PX4 确实融合成功。
- 启动单机任务时由 `deploy/run_a_solo_mocap.sh` 带起动捕源、桥接和预检；必须看**当次** PX4 EV 融合标志及本地位置/速度有效，不以“桥接 forwarded 增长”代替融合成功。
- 当前机上 `a_solo.yaml` 的 `site_checked=false`、`payload_removed=false` 未被本轮改写。前一次地面预检还发现现有 PX4 的围栏动作、RC 输入、`CBRK_FLIGHTTERM`、起飞/降落速度及垂直速度参数未满足单机飞行门禁；这些失败保留，不能靠改配置声明或绕过自检起飞。
- 仓库旧的室内 `fcu_params.py` 检查条件仍要求 `EKF2_BARO_CTRL=0`，与本次成功的 `BARO_CTRL=1、HGT_REF=3` 不一致。正式飞行前应按实测融合组合修正并验证检查条件，而不是把 PX4 改回本次未通过的组合。
- 飞行桥接仍使用近似的杆臂偏移及 Jetson 接收时间；`sample_time_verified=false`，不能把约 870 µs 的软件消息时间差当成相机采集到 PX4 融合的端到端延迟或位置精度证明。实际飞行还需通过当次现场检查、RC 接管和完整飞行前自检。

本轮最终没有飞行或解锁，也没有把地面试验的临时桥接留成常驻进程。
